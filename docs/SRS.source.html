1. Introduction / Pengenalan

1.1 Purpose / Tujuan

This Software Requirements Specification (SRS) defines the functional and non-functional requirements, the technology stack and its justification, and the forward roadmap for e-Pili Bomba Kunak Version 2 (V2) — a mobile-first web application used by BBP Kunak officers to locate fire hydrants (pili bomba), record inspections, and maintain the legally-controlled inspection record card (Kad Rekod Pili Bomba) under MS ISO 9001:2015 procedure PS-8.

Tujuan: Dokumen ini menetapkan keperluan berfungsi dan bukan-berfungsi, teknologi yang digunakan beserta justifikasi, dan pelan masa hadapan bagi sistem e-Pili Bomba Kunak Versi 2 — aplikasi web mudah alih untuk pegawai BBP Kunak mengesan pili bomba, merekod pemeriksaan, dan menyelenggara Kad Rekod Pili Bomba di bawah prosedur MS ISO 9001:2015.

1.2 Scope / Skop

The system provides: an interactive hydrant map, a two-page inspection record card, digital signatures, an inspection dashboard, a shared inspection schedule (jadual), role-based access, and full offline capability. It is live at epilibomba.com, currently serving one district (Kunak, Sabah), and is architected to expand to additional districts and, in future, state/national scale without re-writing the map engine. The user-facing language is Bahasa Malaysia.

Skop: Sistem menyediakan peta pili bomba interaktif, kad rekod pemeriksaan dua muka surat, tandatangan digital, papan pemuka pemeriksaan, jadual pemeriksaan dikongsi, kawalan akses mengikut peranan, dan keupayaan luar talian penuh. Kini melayani satu daerah (Kunak) dan direka untuk berkembang ke daerah lain tanpa menulis semula enjin peta.

2. Overall Description / Perihal Keseluruhan

2.1 Product Perspective / Perspektif Produk

A self-contained web SPA delivered as a static bundle from a CDN, talking to a managed PostgreSQL backend (Supabase) over HTTPS. There is no custom application server: the browser is the client, and all business rules that matter for integrity are enforced in the database (RLS policies + triggers). V1 (a single static index.html) remains deployed and untouched as the one-minute rollback.

2.2 Product Functions / Fungsi Produk

  • Interactive hydrant map with clustering, status filters, zone filters, and place search.
  • Two-page inspection record card (Kad Rekod) with automatic card growth and permanent signed rows.
  • Digital signature capture, reusable profile signature, and print-accurate signature rendering.
  • Inspection dashboard (derived — stores no numbers of its own) with a hand-built 3D donut.
  • Shared inspection schedule (jadual), admin-writable.
  • Role-based access (viewer / admin) enforced by RLS.
  • Full offline operation with automatic sync and conflict recovery.

2.3 User Classes & Characteristics / Kelas Pengguna

ClassRightsNotes

AdminRead all; write (edit records, sign, add hydrants, edit jadual).Writes are scoped to the officer's own district.

Kelas pengguna: Viewer (baca sahaja), Admin (baca & tulis dalam daerah sendiri), dan Upper-admin/Pengurus Daerah (dirancang) yang menguruskan akaun dalam daerahnya.

2.4 Operating Environment / Persekitaran Operasi

  • Client: modern mobile browsers (Android/iOS), used one-handed in the field, sometimes in gloves, often on weak/intermittent signal.
  • Delivery: static bundle on Cloudflare Pages (global CDN + edge).
  • Backend: Supabase (PostgreSQL 15, Auth, Storage) — project isxfhocfkjamjchmicwq.
  • Map tiles: OpenStreetMap via Leaflet.

2.5 Design & Implementation Constraints / Kekangan

  • Legal record: a signed Kad Rekod row is permanent — never editable, clearable, or deletable — enforced in RLS and an independent trigger and the client.
  • Security: script-src 'self' — no third-party scripts; all vendor libraries self-hosted. Audit identity is taken from the database JWT, never the request body.
  • Print fidelity: the record card is tuned to the millimetre for A4/Letter; print CSS order is load-bearing.
  • Reads global, writes district-scoped (mutual aid between stations).
  • No data loss with no signal — offline work is parked and synced.

2.6 Assumptions & Dependencies / Andaian & Kebergantungan

  • Supabase remains available and within plan limits (free tier today — see Section 5, item 7).
  • Cloudflare Pages remains the host; the DNS custom domain is the rollback switch.
  • Each officer has an individual login (signatures attribute who signed).

3. Technology Stack & Rationale / Teknologi & Justifikasi

Each technology below is stated with what it is, the version in use, and why it was chosen for this specific government field application.

3.1 Vite (build tool — v8.2.1)

What: a fast front-end build tool and bundler that compiles Vue single-file components into an optimised static bundle.

Why chosen: V2 needs a build step (V1 had none), and Vite gives a predictable, single-artifact output that suits the strict security posture: one external CSS file (cssCodeSplit:false) so the millimetre-tuned print stylesheet arrives in a known order; no inline scripts, so the CSP can stay script-src 'self' with no 'unsafe-inline'/'unsafe-eval'; and nothing silently inlined (assetsInlineLimit:0). It is fast enough that the whole app builds in ~1 second, keeping the release gate cheap.

Vite: alat binaan pantas yang menghasilkan satu bundle statik. Dipilih kerana menyokong dasar keselamatan ketat (tiada skrip luaran) dan susunan CSS cetakan yang tepat untuk Kad Rekod.

3.2 Vue 3 (UI framework — v3.5.41)

What: a progressive, component-based JavaScript framework for building reactive user interfaces.

Why chosen: V1 was one 3,600-line file that had become hard to change safely. Vue 3's component model breaks the app into testable, single-responsibility pieces (map, card, dashboard, schedule) while keeping a gentle learning curve for a small team. The runtime-only build is used deliberately — no template compiler in the browser — which removes new Function/eval and lets the CSP stay strict. Vue's reactivity drives the live dashboard and offline-sync indicators without manual DOM wiring.

Vue 3: kerangka antara muka berasaskan komponen. Dipilih untuk memecahkan aplikasi kepada bahagian yang boleh diuji dan diselenggara, sambil mengekalkan keselamatan (tiada penyusun templat dalam pelayar).

3.3 Pinia (state management — v3.0.3)

What: the official state-management library for Vue 3 — centralised, reactive stores.

Why chosen: the app has genuinely shared state (the signed-in session, the register, scope filters, the offline queue) read by multiple components. Pinia gives one source of truth for that state, and — critically for this app — it enabled a clean split between pure logic modules (*-logic.js, no framework, no browser) and thin Pinia stores. That split is what lets the most dangerous code (the offline sync decision table) be unit-tested in isolation against the V1 baseline.

Pinia: pengurusan keadaan rasmi untuk Vue. Dipilih kerana membolehkan satu sumber kebenaran untuk data dikongsi, dan memisahkan logik tulen (boleh diuji) daripada antara muka.

3.4 SQL / PostgreSQL (database engine — PostgreSQL 15, via Supabase)

What: a mature, standards-compliant relational database; the data is modelled in SQL tables with constraints, Row-Level Security policies, and triggers.

Why chosen: the Kad Rekod is a legal record, so integrity cannot live in the client. PostgreSQL enforces the rules where they cannot be bypassed: RLS decides who may read/write; a trigger makes signed rows permanent independently of the app; the audit column is stamped from the login token, not the request body. SQL also scales trivially to national volume (~100k rows) with ordinary indexes, and its DR scripts (sql/) are the exact artefact a recovery re-applies.

SQL / PostgreSQL: pangkalan data hubungan. Dipilih kerana integriti rekod undang-undang dikuatkuasakan di pangkalan data (RLS + pencetus), bukan di pelayar — baris bertandatangan kekal selamanya.

3.5 Supabase (backend platform — client v2.112.0)

What: a managed backend built on PostgreSQL, bundling the database, authentication, file storage, and auto-generated APIs.

Why chosen: a small team needed a production backend without operating servers. Supabase provides Auth (individual officer logins), Storage (signature images), and a Postgres API in one managed service — with RLS as the single, database-level security model across all of them. It removes the need for a custom application server entirely: the browser talks to Supabase directly, and every row is gated by RLS evaluated as the calling user. This keeps operational burden low (fitting the single-maintainer reality) while keeping integrity high.

Supabase: platform backend terurus atas PostgreSQL (pangkalan data + log masuk + storan). Dipilih supaya pasukan kecil mendapat backend produksi tanpa mengurus pelayan, dengan keselamatan RLS satu lapisan.

3.6 Cloudflare (hosting & CDN — Cloudflare Pages)

What: a global content-delivery network and static-site host (Cloudflare Pages) with edge caching and security headers.

Why chosen: the app is a static bundle, so a CDN is the correct, cheapest, and fastest host — pages load quickly on weak field connections from an edge near the user. Cloudflare Pages builds the repository directly and serves it, applies the security headers (_headers: CSP, HSTS, geolocation=(self) for "Guna Lokasi Saya"), and — importantly — the rollback is a one-minute DNS switch back to the previous Pages project. Hashed, immutable asset caching plus a no-cache HTML index prevents stale deploys.

Cloudflare: rangkaian penghantaran kandungan (CDN) & hos laman statik. Dipilih kerana pantas di talian lemah, murah, menguatkuasakan pengepala keselamatan, dan membolehkan rollback dalam satu minit.

4. Specific Requirements / Keperluan Khusus

4.1 External Interface Requirements / Antara Muka Luaran

4.1.1 User interfaces

  • Mobile-first, Bahasa Malaysia UI; large touch targets; no zoom-on-focus; no horizontal scroll; high contrast for sunlight.
  • Header tabs: Peta Pili (map), Dashboard, Profil; hamburger navigation below 640px.

4.1.2 Software / communications interfaces

  • HTTPS to the Supabase REST/Realtime/Storage endpoints; JWT auth; RLS enforced server-side.
  • Map tiles fetched from OpenStreetMap; geolocation API for "Guna Lokasi Saya".

5.2 Technical roadmap / Pelan Teknikal

5.2.1 District #2 activation (do when a second station is willing)

The district-ready foundation is already built (a district column, can_write() scoping writes to the officer's own district, reads global). Activation adds the upper_admin (district-manager) role tier, an in-app account-provisioning panel with district-scoped profiles RLS and self-escalation guards, and an All › Kunak › Tawau selector. Run one extra district for three months before designing for ten.

Daerah #2: asas sudah dibina (lajur daerah + kawalan tulis mengikut daerah). Pengaktifan menambah peranan Pengurus Daerah, panel pengurusan akaun, dan pemilih daerah. Jalankan satu daerah tambahan selama tiga bulan dahulu.

5.2.2 National-scale map & geography (future)

Scaling toward state and eventually national volume (~100k hydrants) adds a state tier above district. The map scales without a WebGL/MapLibre rewrite via three legs: (a) state/district filter, (b) bounding-box/viewport loading on a spatial index, and (c) server-side count-bubble aggregation when zoomed out. The hard part is governance (roles/tenancy/audit one layer deeper), not the map.

Skala nasional: menambah lapisan negeri. Peta berskala tanpa menulis semula enjin (penapis + muatan mengikut paparan + agregat kiraan). Bahagian sukar ialah tadbir urus peranan, bukan peta.

5.3 Sequencing / Urutan

Golden rule: settle the organisational actions (5.1 items 2–9) before onboarding district #2 — that event is exactly what turns "runs on one person's goodwill" from acceptable into negligent. In the words of the roadmap: one extra district generates answers; ten generate problems.
Peraturan emas: selesaikan tindakan organisasi (item 2–9) sebelum memulakan daerah kedua. Satu daerah tambahan memberi jawapan; sepuluh daerah memberi masalah.
